# Story 2.1 — Schema profiles e trigger de sincronização

## Status

**Ready** — Validado pelo @po (Pax). GO 9/10. Liberado para @dev.

---

## Story

**Como** dev,
**eu quero** uma tabela `profiles` espelhando `auth.users` via trigger,
**para que** metadados de usuário (username, nome, bio, avatar, tema) fiquem separados da tabela gerenciada pelo Supabase Auth.

---

## Acceptance Criteria

> Fonte canônica: `docs/prd.md` § 6 — Epic 2, Story 2.1. DDL técnico em `docs/architecture.md` § 9.2.

1. Migration cria tabela `profiles` com: `id uuid PK references auth.users(id) on delete cascade`, `username citext unique not null`, `display_name text`, `bio text check (char_length(bio) <= 160)`, `avatar_url text`, `theme text not null default 'light' check (theme in ('light','dark','accent'))`, `created_at timestamptz default now()`, `updated_at timestamptz`.
2. Unicidade case-insensitive de `username` garantida (via tipo `citext` + `UNIQUE` — ver Dev Notes sobre reconciliação com o PRD).
3. Trigger `on auth.users insert` cria linha em `profiles` com `username` derivado do metadata do signup (`raw_user_meta_data->>'username'`).
4. Trigger `updated_at` atualiza o campo em todo `UPDATE` (reusa `set_updated_at()` da baseline).
5. Migration aplicada com sucesso no projeto Supabase `development` via `supabase db push`.
6. Teste de integração (rodando contra `development`): inserir em `auth.users` resulta em linha correspondente em `profiles`.

### DDL canônico (copiar deste bloco)

[Source: architecture.md § 9.2]
```sql
CREATE TABLE public.profiles (
  id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  username citext UNIQUE NOT NULL,
  display_name text,
  bio text CHECK (bio IS NULL OR char_length(bio) <= 160),
  avatar_url text,
  theme text NOT NULL DEFAULT 'light' CHECK (theme IN ('light', 'dark', 'accent')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz,
  CONSTRAINT username_format CHECK (
    char_length(username) BETWEEN 3 AND 30
    AND username ~ '^[a-z][a-z0-9_]*$'
  )
);

CREATE TRIGGER profiles_set_updated_at
  BEFORE UPDATE ON public.profiles
  FOR EACH ROW
  EXECUTE FUNCTION public.set_updated_at();

CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  INSERT INTO public.profiles (id, username)
  VALUES (
    NEW.id,
    NEW.raw_user_meta_data->>'username'
  );
  RETURN NEW;
END;
$$;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_new_user();
```

### ⚠️ Reconciliação PRD × Arquitetura (AC 2)

O PRD Story 2.1 AC2 pede "Índice `unique` em `lower(username)`". A arquitetura § 9.2 (nota canônica) determina que **`username citext UNIQUE` já garante comparação case-insensitive**, dispensando índice adicional em `lower(username)`. **Seguir a arquitetura** — `citext UNIQUE` é suficiente. [Source: architecture.md § 9.2 — "o tipo já garante comparação case-insensitive, então UNIQUE (username) cobre o caso ... sem índice adicional"]

### Regex de username no banco vs. helper TS

A CHECK `username_format` usa `^[a-z][a-z0-9_]*$` (3-30 chars, começa com letra). O helper TS da **Story 2.3** deve casar com esta mesma regra (normaliza para lowercase antes de validar). A app normaliza para lowercase antes do `signUp`. [Source: architecture.md § 9.2]

### Dependências (baseline da Story 1.4)

- `citext` e `pgcrypto` já instalados pela migration baseline `20260527025356_baseline.sql`.
- Função `public.set_updated_at()` já existe — apenas referenciar no trigger.
[Source: architecture.md § 9.1]

### SECURITY DEFINER no trigger

`handle_new_user()` roda como `SECURITY DEFINER` para inserir em `profiles` no caminho do signup sem depender de RLS (que não existe no MVP). `SET search_path = public` previne hijack de search_path. [Source: architecture.md § 9.2]

### Sem RLS nesta story

Autorização é app-layer no MVP. RLS em `profiles` é escopo do Epic 6 (Story 6.1). Não adicionar policies aqui. [Source: prd.md NFR3; Story 2.2 nota de reconciliação v1.1]
