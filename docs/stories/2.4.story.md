# Story 2.4 — Signup com e-mail, senha e username

## Status

**Draft** — Aguardando validação do `@po` (Pax).

---

## Story

**Como** novo usuário,
**eu quero** me cadastrar com e-mail, senha e username,
**para que** eu tenha minha página pública reservada.

---

## Acceptance Criteria

> Fonte canônica: `docs/prd.md` § 6 — Epic 2, Story 2.4.

1. Página `/signup` com form: e-mail, senha (mín. 8 chars), confirmação de senha, username.
2. Validação client + server (checks inline + helper `validateUsername` da Story 2.3); username checado contra duplicatas no DB.
3. Server Action `signUp` chama `supabase.auth.signUp()` passando `options.data.username`.
4. Trigger da Story 2.1 cria `profile` com o username informado.
5. Supabase Auth envia e-mail de verificação; página redireciona para `/signup/check-email` com instrução clara.
6. _(deferido para Epic 6)_ Rate limiting de signup (5/h/IP) — não aplicável no MVP.
7. Username duplicado retorna erro claro no form, sem criar usuário em `auth.users`.
8. Teste de integração (contra `development`): signup → registro em `auth.users` + `profiles`.

## Dev Notes

> **CRITICAL:** Informação técnica de `docs/architecture.md` e `docs/prd.md`. Nada inventado.

### Pré-requisitos já aplicados (config as code)
- **`enable_confirmations=true`** já está ativo nos projetos Supabase (aplicado via `config push` no setup do epic). O signup já dispara e-mail de verificação obrigatório. [Source: supabase/config.toml; commit chore EPIC-2]
- Template de confirmação pt-BR já configurado (Story 2.5 cobre o callback).

### Server Action `signUp`
Catálogo: `signUp` / input `{ email, password, username }` / sem revalidação. [Source: architecture.md § 5.2]
Convenção de action: `'use server'`, validação inline, retorna `ActionResult`, nunca lança. [Source: architecture.md § 5.1; exemplo § 9.1]

### Fluxo (sequence)
`/signup` → `signUp` → checks inline → SELECT username existente → `auth.signUp({data:{username}})` → trigger cria profile → e-mail enviado → redirect `/signup/check-email`. [Source: architecture.md § 8.1]

### Trigger cria o profile
O `handle_new_user()` (Story 2.1) lê `raw_user_meta_data->>'username'`. Por isso `options.data.username` é obrigatório no `signUp`. [Source: architecture.md § 9.2]

### Sem RLS / authz app-layer
Nenhuma policy nesta story. [Source: prd.md NFR3]

### Dependências
Depende de **2.1** (trigger/profiles) e **2.3** (`validateUsername`). Wave 2.
