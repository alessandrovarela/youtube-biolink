# Story 3.1 — Schema `links`

## Status

**Ready for Review** — implementada pelo `@dev` (YOLO, Wave 1). Migration aplicada no dev; typecheck/lint/integração verdes. Aguarda QA Gate (`@qa`).

---

## Story

**Como** dev,
**eu quero** uma tabela `links` com DDL e índices adequados,
**para que** usuários tenham onde gravar seus links e a página pública consiga lê-los.

---

## Acceptance Criteria

> Fonte canônica: `docs/prd.md` § 6 — Epic 3, Story 3.1. DDL: `architecture.md` § 9.3.

1. Migration cria tabela `links` com: `id uuid PK default gen_random_uuid()`, `profile_id uuid not null references profiles(id) on delete cascade`, `title text not null check (char_length(title) between 1 and 60)`, `url text not null`, `position int not null default 0`, `is_active boolean not null default true`, `created_at timestamptz default now()`, `updated_at timestamptz`.
2. Índice em `(profile_id, position)` para ordenação.
3. _(deferido para Epic 6)_ RLS e policies são endereçadas na Story 6.2. No MVP, autorização é application-layer: Server Actions filtram por `profile_id = auth.uid()`; leitura pública filtra `is_active = true` no próprio query.
4. Trigger de `updated_at` (reusa `public.set_updated_at()` da baseline — Story 1.4).
5. Migration aplicada com sucesso em `development` via `supabase db push`.
6. Teste de integração valida via Server Action: usuário A não consegue UPDATE/DELETE em link de usuário B (o filtro por `auth.uid()` rejeita a operação); query pública da página `/[username]` retorna apenas links `is_active = true` do profile correto.

## Dev Notes

> **CRITICAL:** DDL e modelo vêm de `docs/architecture.md`. Nada inventado (Artigo IV).

### DDL canônica (`architecture.md` § 9.3)
Usar exatamente a DDL da arquitetura. O `CHECK (url ~ '^https?://')` é **última linha de defesa** — a sanitização primária (rejeitar `javascript:`/`data:`/etc.) acontece no TS via `sanitizeLinkUrl` (Story 3.2). [Source: architecture.md § 9.3 nota]

### Sem RLS no MVP
RLS/policies de `links` são a Story 6.2 (Epic 6). Autorização aqui é **app-layer**: mesmo padrão de `profiles` (Story 2.1) — filtro `profile_id = user.id` nas Server Actions; leitura pública filtra `is_active = true`. [Source: architecture.md § 2.5 Application-Layer Authorization; prd.md Story 3.1 AC3]

### Relacionamento
`links.profile_id → profiles.id ON DELETE CASCADE`. Deletar profile remove os links. [Source: architecture/ER.md; architecture.md § 9.3]

### Baseline reusada
`gen_random_uuid()` (pgcrypto) e `set_updated_at()` já existem (baseline Story 1.4). Não recriar. [Source: architecture.md § 9.1]

### Dependências
Nenhuma story-dependência. Requer PRE-1 (ER consolidado — `docs/architecture/ER.md`, já entregue). Wave 1 (paralela com 3.2 e 3.6).
