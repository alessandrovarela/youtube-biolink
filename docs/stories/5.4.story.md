4. Benchmark documentado: ~10k cliques seeded no `development`; agregação **<100ms** (ver Resultado do Benchmark).
5. Testes de integração com seed validam contagem por link, série diária e isolamento por profile.

## Dev Notes

> **CRITICAL:** Nada inventado (Artigo IV). View, helpers e authz derivam de PRD 5.4 + EPIC-5-EXECUTION (decisão #4) + padrão de `public-page.ts`.

### Decisão: view REGULAR, não materializada
A `link_click_daily` é uma **view regular**. Uma materialized view exigiria estratégia de `REFRESH` (trigger/cron) e serviria dados potencialmente stale — complexidade injustificada para o volume do MVP. O benchmark (10k cliques) confirma que a agregação regular fica **muito abaixo** do alvo de 100ms, apoiada no índice `(link_id, clicked_at desc)` da Story 5.1. Materializar fica como otimização futura se o volume crescer. [Source: EPIC-5-EXECUTION.yaml decisão #4]

### Decisão: authz application-layer via link_ids (sem RLS)
Consistente com Epics 2-4, `link_clicks`/`link_click_daily` **não têm RLS no MVP** (deferido p/ Story 6.3). Os helpers buscam primeiro os `link_ids` do próprio profile (`links.profile_id = profileId`, equivalente ao `auth.uid()` do Epic 6) e só então consultam a view restrita a esses ids (`.in('link_id', ...)`). Optei por **duas queries** em vez de um join embutido na view porque **a view não declara FK para `links`** — o PostgREST não inferiria o relacionamento de forma confiável. O resultado é idêntico ao do join por `profile_id`: nunca lemos cliques de links de outro profile. É o mesmo padrão de duas leituras de `lib/queries/public-page.ts`. [Source: architecture.md § 2.5; public-page.ts]

### Assinaturas (a Story 5.5 consome)
```ts
getClicksByLink(supabase: SupabaseClient, profileId: string): Promise<LinkClickTotals[]>
getDailyClicks(supabase: SupabaseClient, profileId: string, days: number): Promise<DailyClickPoint[]>

interface LinkClickTotals { link_id: string; title: string; total: number; last7: number; last30: number }
interface DailyClickPoint { day: string /* 'YYYY-MM-DD' UTC */; clicks: number }
```
O client é **injetado** (1º parâmetro), como em `public-page.ts` — a 5.5 passa um client server-side. `getClicksByLink` já entrega `last7`/`last30` (baratos: a série por link já é lida), cobrindo as colunas 7d/30d da tabela do dashboard (PRD 5.5 AC1). `getDailyClicks` devolve série **contínua** (dias sem clique preenchidos com 0) ordenada do mais antigo ao mais recente, pronta para o gráfico (PRD 5.5 AC2). Janelas: `last7`/série de 7 = hoje + 6 dias anteriores (UTC); `last30` = hoje + 29.

### Datas em UTC
A view faz `date_trunc('day', clicked_at)::date` (timezone da sessão = UTC no Supabase). Os helpers calculam os cutoffs em UTC e comparam strings `YYYY-MM-DD` (lexicográfica == cronológica). O seed fixa 12:00 UTC para determinismo do dia.

### Dependências
Depende da Story 5.1 (schema + índice). Wave 2 (paralela com 5.2). Independe de 5.2/5.3 — constrói sobre o schema.

## Resultado do Benchmark

**Setup:** projeto Supabase `development` (cloud, `rjsvkwjgsctqsswrospx`). 1 profile, 5 links, **10.000 cliques** (2k/link) espalhados por 90 dias, via bulk insert chunked (`seed-clicks.ts`). Executado com `RUN_CLICKS_BENCH=1 pnpm test tests/integration/clicks-benchmark.test.ts`.

| Medida | Valor |
|--------|-------|
| `getClicksByLink` (wall-clock, inclui rede) | **338,0 ms** |
| `getDailyClicks(30)` (wall-clock, inclui rede) | **322,4 ms** |
| RTT mediano a um `select` trivial (Supabase cloud) | ~161 ms |
| Query da view `link_click_daily` (mediana, ≤1000 linhas) | ~154 ms (≈ RTT) |
| **Agregação DB-side (delta view − RTT trivial)** | **< 10 ms** ✅ |

**Interpretação:** o wall-clock de ~330 ms é **dominado pela rede** — cada helper faz **2 round-trips sequenciais** ao Supabase cloud (fetch dos link_ids do profile + query da view), ~2 × 161 ms. A **agregação em si** (a "query de agregação" do AC4) é indistinguível de um round-trip vazio → **< 10 ms, muito abaixo do alvo de 100 ms**, graças ao índice `(link_id, clicked_at desc)` da Story 5.1. Não foi necessário materializar a view.

> Nota: medido de uma máquina local contra o Supabase cloud gerenciado; não foi possível rodar `EXPLAIN ANALYZE` direto (sem senha do DB de dev à mão — só via PostgREST/anon). A decomposição RTT vs. query isola o custo de DB de forma conservadora.
