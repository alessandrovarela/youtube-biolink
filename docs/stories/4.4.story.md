# Story 4.4 — Aplicação de tema na página pública + validação a11y WCAG AA

## Status

**Ready for Review** — implementada pelo `@dev`. A página pública `/[username]` (RSC/SSR)
lê `profile.theme` e aplica a classe do tema no root da própria página; refactor leve
alinhado ao ui_kit `public-profile` usando tokens/primitivos; contraste WCAG AA validado
por teste unitário nos 3 temas. Gates verdes. Aguarda QA Gate (`@qa`).

---

## Story

**Como** visitante de um perfil público,
**eu quero** ver a página `/[username]` já renderizada no tema escolhido pelo dono (sem flash),
**para que** a experiência seja consistente com o dashboard e legível (contraste adequado).

---

## Acceptance Criteria

1. `app/[username]/page.tsx` lê `profile.theme` e aplica a classe do tema (via `resolveThemeClass`)
   no ROOT da página server-side (SSR). Como o `<html>` mora no root layout e não conhece o tema
   do dono, o conteúdo é envolto num container que recebe a classe do tema. Os seletores de tema
   em `globals.css` passam a cobrir também o container (`html.theme-*, .theme-*`), garantindo que
   os tokens resolvam no escopo do container sem quebrar o dashboard (que aplica no `<html>`).
2. Sem FOUC/flash: a classe é renderizada no HTML do servidor (RSC) — nenhuma troca client-side.
3. CSS variables resolvem para os valores do tema escolhido; visual usa tokens/primitivos
   (Avatar com fallback, tipografia, spacing) alinhado ao ui_kit `public-profile`. Sem regressão:
   links ativos na ordem, nova aba com `rel="noopener noreferrer"`, 404 custom, `revalidate` ISR.
4. Dashboard e página pública mostram o MESMO tema do usuário (o do dono, na pública).
5. Contraste WCAG AA (≥4.5:1 texto normal; ≥3:1 large/UI) validado por teste unitário nos 3 temas
   para os pares críticos (fg/bg, muted-fg/bg, accent-fg/accent). Resultados na tabela abaixo.
6. Teste: a página pública renderiza com a classe de tema correta a partir de `profile.theme`
   (via render RTL da view presentacional).

## Dev Notes

### Aplicação de tema fora do `<html>` (AC1)
O root layout (`app/layout.tsx`) é compartilhado por dashboard e página pública e não tem como
saber o tema do **dono** da página pública. Solução: a página pública aplica a classe num
**container próprio**. Para que as CSS variables resolvam nesse escopo (e não só em `html.theme-*`),
os blocos de tema em `globals.css` ganharam o seletor de classe genérico:
`html.theme-dark, .theme-dark { … }` (idem accent). O dashboard (Story 4.3) continua aplicando no
`<html>` e não é afetado — o seletor `html.theme-*` segue válido.

### Sem FOUC (AC2)
É RSC/SSR: a classe já vem no HTML do servidor. Diferente do dashboard (client, com script inline
anti-flash), a pública não faz nenhuma troca client-side — o markup nasce no tema certo.

### Primitivos/tokens (AC3)
`Avatar` (client, fallback de iniciais) usado dentro da RSC; link-rows e tipografia via utilities de
token (`bg-surface`, `border-border`, `text-muted-fg`, `shadow-[var(--shadow-sm)]`) espelhando o
ui_kit `public-profile`. Funcionalidade preservada: ordem por `position` (query), `target="_blank"`
+ `rel="noopener noreferrer"`, 404 custom, ISR `revalidate=60`.

### Validação de contraste (AC5)
Sem navegador no ambiente, o teste lê os hex dos tokens direto de `app/globals.css` e calcula a razão
de contraste pela fórmula oficial do W3C (luminância relativa sRGB → linear). Limiares:
texto normal 4.5:1; UI/large 3:1.

## Tabela de Contraste WCAG 2.1 AA (3 temas)

| Tema   | Par                 | Uso                         | Razão   | Limiar | Resultado |
|--------|---------------------|-----------------------------|---------|--------|-----------|
| light  | fg / bg             | texto de corpo (normal)     | 17.85:1 | 4.5:1  | ✅ PASS   |
| light  | muted-fg / bg       | username/secundário (normal)| 7.58:1  | 4.5:1  | ✅ PASS   |
| light  | accent-fg / accent  | rótulo botão primário (UI)  | 5.17:1  | 3.0:1  | ✅ PASS   |
| dark   | fg / bg             | texto de corpo (normal)     | 15.12:1 | 4.5:1  | ✅ PASS   |
| dark   | muted-fg / bg       | username/secundário (normal)| 7.30:1  | 4.5:1  | ✅ PASS   |
| dark   | accent-fg / accent  | rótulo botão primário (UI)  | 7.36:1  | 3.0:1  | ✅ PASS   |
| accent | fg / bg             | texto de corpo (normal)     | 12.59:1 | 4.5:1  | ✅ PASS   |
| accent | muted-fg / bg       | username/secundário (normal)| 5.46:1  | 4.5:1  | ✅ PASS   |
| accent | accent-fg / accent  | rótulo botão primário (UI)  | 3.12:1  | 3.0:1  | ✅ PASS*  |

\* **Débito QUITADO na Story 6.6 (2026-07-19).** À época desta story, `accent-fg` (#ffffff) sobre
`accent` (#d97757) no tema *accent* rendia **3.12:1** — atendia AA para **componentes de UI e texto
grande** (1.4.11 / 1.4.3, ≥3:1), mas **não** para texto normal (<4.5:1), afetando o rótulo do
`Button variant="primary"` (font-medium, 14–15px). A **página pública não usa
`accent-fg`-sobre-`accent` como texto** (os link-rows usam `fg`/`bg`/`surface`; o footer usa `fg`),
então nunca houve regressão de legibilidade na pública.
**Resolução:** a Story 6.6 escureceu `--color-accent` do tema accent de `#d97757` → **`#b06046`**
(escala RGB uniforme, matiz preservado), levando o par a **4.56:1**, e elevou o limiar do teste de
3.0 → **4.5**. A tabela acima registra os valores históricos do Epic 4; os valores correntes estão
em `docs/design-system.md` §5.1.
